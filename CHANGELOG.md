# Changelog

All notable changes to Dasha Framework are documented here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project
follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- In the system menu's Themes, Default and Dark both had D as their letter, so pressing D could only ever choose Default. Dark now has A (D&ark). Each built-in theme takes the first letter of its name that no theme before it has, and C is kept for Colours file.
- In the Window menu, Minimise and Next window both had N, so Next window could not be chosen by its letter. Next window now has T (Nex&t window).
- With a menu open, pressing Right on an item with no submenu, or Left in the drop-down, when there is no other menu on the bar to go to (such as the system menu on a desktop with no applications running, or when the other menus are inert behind a dialog), opened the same menu again, sending the highlight back to its first item. Now nothing happens, and the highlight stays where it was.
- Settings... and the shortcuts table described the `text_*` actions as working in text boxes only, though most work in text areas too, and `open_menu` as opening the system menu, though it opens the first menu on the bar (the system menu only on the desktop). The desktop's help left Applications and Run... out of the system menu's items, and said that every minimised window is listed in the system menu, though an application's are listed in its Window menu. All now say what actually happens.

### Changed

- A mnemonic letter belongs to one item of a menu, and to one title on the menu bar. If a later item or title marks the same letter (in either case), the first keeps it, and the later one is drawn and treated as having no letter. This applies to the menu bar's menus and to context menus. Before, both letters were highlighted, the letter chose whichever of them was enabled first, and a greyed-out first item passed the letter on to the second.
- `Menu.check_mnemonics()` and `MenuBar.check_mnemonics()` raise the new `DuplicateMnemonicError` (a `ValueError`) if two items of a menu, or of any submenu, or two titles on the bar, mark the same letter. `on_open` fills each menu in first, so menus like Themes are checked as they would be shown. `Menu.mnemonics()` gives each item's letter as it works, and `dasha.menu.unique_mnemonics(labels, strict=False)` does the same for any labels. Dasha Framework's tests now check every menu of the desktop and of the example applications this way, so a repeated letter fails the tests.
- Extended the dasha namespace `__path__` in order to enable packages to share the dasha namespace.
- `NO_COLOR` now keeps colour out altogether. `dasha desktop`, and an application running on its own, start in the Monochrome theme whenever it is set, and stay in it: the system menu's Themes and the Appearance page of Settings... are greyed out, `set_theme` refuses any other theme (returning `False`), and no theme is remembered, so the one chosen before is used again once `NO_COLOR` is removed. Before, a theme chosen from the menu, a colours file naming a base, or `--colours` came before `NO_COLOR`, and any theme could be chosen while running. `--monochrome`, and choosing Monochrome from Themes, still leave the other themes there to choose.
- `Tabs` pages can be disabled: `disable(*indexes)`, `enable(*indexes)`, `is_enabled(index)` and the `disabled` set, as for check boxes and radio buttons. A disabled page's tab is greyed out (the new `tabs.disabled` colour role), its letter is free, and it cannot be chosen by key, click or letter.
- The protocol between the desktop and applications in processes of their own is now version 2, so that a theme can carry roles added since the first release (`theme.NEWER_ROLES`). An application of the first release still connects, and is sent the theme without them, as it would refuse a role it does not know. Colours and theme files leave such a role out while it is as the base theme has it, so an earlier release can still read them.

## [0.0.1] - 2026-11-14

The first public release of Dasha Framework, a text-mode desktop and application framework for local and SSH terminals, written in pure Python with no third-party dependencies.

### Desktop, windows and menus

- A desktop of overlapping windows drawn with code page 437 characters and drop shadows, with a menu bar along the top and a status bar along the bottom. The status bar names the active application, or shows `Dasha Desktop` when none is active, and lists the keys of the focused widget. For text boxes, password boxes, autocomplete boxes, spin boxes and text areas it leaves out the keys that only edit text (cut, copy, paste, select all, undo, redo, clear and delete line); those keys still work and can be remapped, and menus still show them.
- Windows can be moved, resized, maximised, minimised, restored and closed with the mouse or the keyboard, and can never be moved so far off screen that they are lost. Moving a maximised window returns it to its earlier size, and resizing one from its grip starts from its current size; either way it is no longer maximised. When a window's contents do not fit, scroll bars appear on its frame.
- A window can show a footer at the left of its bottom edge (`Window.footer`, or a subclass's `footer_parts`). The footer is made of parts, and the frame draws its own line between them, so the separators always match the frame, whether or not the window is active. The horizontal scroll bar starts after the footer, and the footer is hidden when the window is too narrow for both. Notepad uses it to show `☼` when a file has unsaved changes, followed by the cursor position as COL:ROW.
- Clicking a key hint on the status bar presses that key: `F10 Menu` opens the menu bar, and a widget's hints do what their keys do.
- Drop-down menus with submenus, mnemonics, shortcut keys and items that can be greyed out. They work with the mouse (hover, click, or press, drag and release), with F10, with Alt and a letter, and with the arrow keys. Context menus open with a right-click or Shift+F10.
- A system menu (`≡`) with About, Help, Settings..., the Applications menu, the running applications to switch between, Run..., Themes, Animations, Command prompt and Shutdown. Every application also gets the same standard Window menu. `Menu(after_window=True)` puts one of an application's menus after the Window menu, as a Help menu usually is; the Demo's Help menu uses it.
- Settings... (`dasha.settings`) changes, from within Dasha Framework, everything that the command line and the settings files configure. Its Appearance page chooses a theme and changes the colours and attributes of every role, with Custom... for an RGB colour, and Load... and Save as... for theme files; its Shortcuts page adds a key to an action by pressing it, removes keys, and loads and saves shortcuts files, refusing any change that would leave no way out by keyboard; its Desktop page turns animations on or off, chooses how colours are drawn (24-bit, 256 or 16 colours), turns showing the mouse on or off, and chooses the applications to start with the desktop; and its Applications page installs and uninstalls applications. Changes show at once, including in applications running in their own processes; OK and Apply save them to the colours file, the shortcuts file and `settings.toml`, and Cancel puts them back.
- The cell under the mouse can be drawn inverted, for terminals that show no mouse pointer. It is off by default, and turned on and off with `` Alt+` `` (the remappable `show_mouse` shortcut, which works wherever the focus is), `--show-mouse`, or Settings...; the last choice is remembered in `settings.toml`.
- A command prompt: Alt+F12 (the remappable `command_prompt` shortcut, which works wherever the focus is), or Command prompt in the system menu, gives the terminal back and runs the user's shell (`COMSPEC` on Windows, `SHELL` elsewhere) until they type `exit`. The desktop is then drawn again in full from what it holds, so programs that drew over its screen meanwhile leave no trace. Applications keep running. Ctrl+C and the like at the shell do not reach the desktop, and Dasha Framework refuses to start a second desktop inside the prompt.
- The desktop fails softly. An unexpected error in its own code is written to a log in `~/.dasha/logs/`, whatever was under way (an open menu, a drag) is put aside, the user is told that their applications are still running and where the log is, and the desktop carries on. Only if the same kind of step (drawing, say) fails five times in a row does it give up and shut down, saying where the log is. Applications run on their own fail softly in the same way.
- Optional animations, turned on and off from the system menu, with the setting remembered. Menus drop down from the menu bar, windows shrink into the status bar when minimised and grow back out of it when restored, and windows zoom between their two sizes when maximised and restored. Each animation takes only a few quick frames.

### Widgets and dialogs

- Widgets (`dasha.widgets`): labels, push buttons, text boxes, password boxes, text areas, check boxes, radio buttons, switches, list boxes, combo boxes, autocomplete boxes, spin boxes, sliders, progress and column bars, scroll bars, paragraphs, group boxes, collapsible areas, tabs, splitters, tables and tree views.
- Text areas can wrap long lines (`word_wrap=True`, off by default). A long line continues on the rows below, broken after a space, and the cursor, the Up and Down keys, clicks and selections all follow the rows on screen. Text areas can also number their lines (`line_numbers=True`, off by default) in a right-aligned column beside the text, which widens once there are more than 999 lines.
- Tree views can select several items (`TreeView(..., multiple=True)`), as list boxes can: Space, Ctrl+A, a click or Shift and a click select items, which stay selected while the items above them are collapsed. `selected_nodes` holds the selected items, in the order of the outline, `set_selected_nodes(nodes)` selects others, and `value` is a tuple of them. `selected=` sets the items selected to begin with, or, with single selection, the item highlighted, expanding the items above it. The Demo's File > Choose folder... picks one of the computer's folders from a tree view, finding each folder's folders only when it is first expanded.
- Over slow connections, keys are read more reliably. After a lone ESC, Dasha Framework waits 100 ms for the rest of a key (`escape_timeout` in `settings.toml`, and Settings...), so an arrow key arriving late is not taken as Escape. Large pastes are decoded in time proportional to their length (16 MB in about 0.02 s), and on Windows an emoji split between two console reads is joined back together.
- Files are saved whole or not at all (`dasha.config.write_atomically`): the settings files, application manifests and Notepad's files are written to a temporary file and then put in place in one step, so a full disk or a crash part-way through a save leaves the old file as it was.
- Text editing with selection, movement by word, undo and redo, a double-click selecting all of a text box's text (and a line of a text area), and a shared clipboard for cut, copy and paste. Widgets can grow with their window and can be nested in containers.
- A click that the widget under the pointer does not use (a right-click with no menu, or the middle button, say) leaves the focus on that widget.
- Modal dialog boxes (`dasha.dialog`), including the ready-made `confirm()`, `information()` and `question()`, and a file dialog (`dasha.filedialog`) for opening and saving files.

### Help

- Help windows. An application offers help by setting `help_folder` to a folder of Markdown files, with `index.md` as the default page. F1 (the `help` shortcut) opens a cyan help window at the topic of the focused widget (`widget.help = "user_name"`), of a container it is in, or of its window (`window.help`), or else the index; without a `help_folder`, or with no pages in it, F1 does nothing. The window has links between pages and to their headings (`other.md#saving`), Back, Forward and Index, and a search of every topic (Ctrl+F), with a clickable row at the top and a shortcut action for each. A link to a web address copies the address to the clipboard rather than opening it. In a dialog, help opens in front of it, and closing it goes back to the dialog as it was. `Application.show_help(topic=None)` shows help from a menu item, and `has_help()` says whether there is any. The Demo has help of its own in `apps/demo_help`.
- `dasha.markdown` shows Markdown as well as a text screen can: headings decorated by level, bold, italics, code, nested lists, block quotes, rules, tables drawn in box characters and wrapped to fit, links, and images as their descriptions, with HTML tags removed. Its colours are the `help.*` roles.
- The desktop has help of its own, in the package's `helppages` folder, which F1 shows when no application is active and in the desktop's own dialogs, and which the system menu's Help opens. An application running on its own does not offer it, and F1 in an application with no help does nothing, on the desktop too. When F1 is pressed for a hosted application that has no window, the desktop sends it a `help` message, which an application that does not know the message ignores.

### Applications

- `Application` (`dasha.application`) owns its menus, windows and dialogs. It can run on its own in a terminal with `Application.run()`, which has the terminal's size before its `start` so that it can fit its windows to the screen, or on the desktop.
- On the desktop, each application runs in its own process and talks to the desktop using a versioned JSON protocol. If an application crashes or hangs, only its own windows are affected: a hung application is marked "(Not responding)" and can be ended, and its dialogs block only its own windows. When an application ends, so does everything it started, and every application ends when the desktop does.
- An application becomes the active one when it first has something to show (its menus, which it always sends, even with none), not when it connects, so the menu bar, the status bar and the system menu's list stay as they were while it loads, and then change together. Started from the desktop, whatever was on the bar stays while it loads, and still works; with no system menu (`dasha APP`), the bar's row shows the desktop's pattern. An application that is connected but has shown nothing after 30 seconds (`AppServer.load_timeout`) is not left waiting silently: the user is asked whether to end it or wait for it. Leaving the desktop does not wait for an application that is still loading, and with `dasha a b`, the end of `a` does not end the desktop while `b` is still loading. Starting a single-instance application again while it loads does nothing.
- A window's own colours work in an application the desktop started as well as in one run on its own: the window sends any of `frame_style`, `inactive_frame_style`, `adjusting_frame_style`, `body_style`, `button_style`, `resize_grip_style` and `scrollbar_style` that differ from the theme's, and the desktop draws its frame in them. The rest follow the theme.
- `PresentationManager.call_from_thread(callback)` has the desktop's own thread call `callback` as soon as it can, from any other thread, waking the loop if it is waiting for input. It works on a desktop of its own and in an application hosted by the desktop alike, so that a thread reading a program's output, say, can update a window. `Terminal.wake` (and `Terminal.is_woken`) cut short a read that is waiting, from any thread; a wake, or a resize, that comes while the rest of an escape sequence is awaited does not cut that wait short.
- `dasha` is told what to run. `dasha desktop` starts the desktop, and applications named after it (`dasha desktop notepad`) start on the desktop, after those that start with it; applications named alone (`dasha notepad`) run on their own. `dasha-desktop` is a command of its own for `dasha desktop` (`dasha-desktop notepad`). Options may come between applications (`dasha desktop -m notepad`). `dasha` with nothing to run shows its usage and an error (exit code 2); `--key-test` and the `--init-...` options need nothing.
- `dasha install-app` installs a script or a `module:Class` by writing a TOML manifest to `~/.dasha/apps/`, optionally with its own virtual environment (`--venv`, `--create-venv`, `--pip`). `uninstall-app` removes one and `list-apps` lists them. Installed applications appear in the Applications menu, can start with the desktop (`autostart`), and can be run on their own. For example, `dasha notepad` looks and behaves just like running the application's script: there is no system menu, and Dasha Framework ends when the application does. No application can have the id `desktop`.
- Applications can be named on the command line by id or by name, in any case: `dasha Notepad` runs the application `notepad`, and `dasha git` one with the id `dasha-github` called Git (`dasha-desktop` and `dasha desktop` too). An id comes first; a name that more than one application has is refused, listing their ids.
- An application running on its own shows no name on the status bar until it is active, not even while it loads, and nothing on its screen names Dasha Framework: the command prompt, and the dialog after something goes wrong, name the application instead (`PresentationManager.program_name`), and the dialogs for an application that is not closing, or that sent something unexpected, do not name Dasha Framework at all.
- An application running on its own logs what goes wrong where its system keeps programs' logs, in a folder named after it: `%LOCALAPPDATA%\Notepad\logs` on Windows, `~/Library/Logs/Notepad` on macOS, and `$XDG_STATE_HOME/notepad/logs` (by default `~/.local/state/notepad/logs`) elsewhere, as `notepad-<time>.log` (`dasha.logs.app_log_folder`). `Application.log_folder` chooses another folder. The desktop's logs are in `~/.dasha/logs`.
- Run... starts an application once without installing it. Usually the name of the script is enough: Run... finds the application class by reading the script (without running it), and finds a virtual environment in the script's folder or the folder above. Both can be changed in its Options area.
- A script inside a package (its folder has an `__init__.py`) is imported as part of that package, so it can import the package's other modules by name: `pgh/app.py` runs as `pgh.app`, and `from pgh.git import ...` works.

### Command-line programs in windows

- Command-line programs can run inside a window. `dasha.pseudoterminal` runs a program in a pseudo-terminal (`os.forkpty` on Linux and macOS, a ConPTY pseudoconsole on Windows 10 version 1809 or later), `dasha.vt` is a VT emulator that keeps what a terminal would show (and `encode_key` turns key names into the bytes a terminal sends), and the `TerminalView` widget puts the two together in a window.
- `TerminalView.default_style` sets the colours of whatever a program leaves in its default colours, blank cells included. By default the terminal Dasha Framework is running in chooses them.

### API

- Names and properties are consistent across the API. Reads that do work are methods: `Terminal.size()`, and the presentation manager's `bar_menus()`, `inert_menus()`, `status()` and `key_hints()`. Reads that only return what is held are properties: `Clipboard.text`, `Shortcuts.overrides`, `TreeNode.path`, `ProgressBar.halves`, `Recovery.message`, `MenuBar.title_spans`, `Window.scroll_bars` and `shown_footer`, `Splitter.divider_rect`, `Container.home_row`, and `AppHost.modal_window`. Boolean queries start with `is_`, `has_` or `can_`: `Rect.is_empty`, `InputDecoder.is_pending` and `is_pasting`, `AppServer.is_busy`, `is_running` (the presentation manager, `Application`, `PseudoTerminal` and `TerminalView`), `PresentationManager.is_resizing`, `MenuItem.is_available`, `Screen.is_alternate` and `is_tracking_mouse`, `Widget.is_shown`, `Container.is_showing_children`, `Paragraph.is_scrollable`, `TextBox.has_more_left` and `has_more_right`, `Terminal.can_report_key_releases` and `is_woken`, `TerminalView.is_mouse_for_program`, `Recovery.has_too_many_failures` and `AppHost.can_take_front`. The same things share a name: `PresentationManager.active_window`, as `Application.active_window`; and `Tabs.selected` and `selected_page` and `TreeView.selected_node`, as `ComboBox.selected` and `selected_item`.

### Security

- An application cannot harm the desktop or other applications. Everything it sends is checked: colours, sizes, one-line text, at most 16 MiB per message, at most 100 windows and 2,000 menu items. An application that sends something unusable is ended on its own. Nor can an application hold up the desktop: messages to it are queued in an outbox, a connection that never completes its handshake is dropped after 10 seconds without delaying others, a flood of messages is handled a little at a time, the messages waiting to be handled are counted and capped (64 MiB for each application, 256 MiB in all, beyond which a flooding application is slowed to the desktop's pace), and the user is asked about any application that never answers whether it may close during shutdown.
- An application cannot impersonate another application, or Dasha Framework itself. The desktop decides its name, and only replaces a name that Run... guessed; and its menus cannot claim the desktop's own keys as shortcuts.
- Only the active application can bring windows to the front. A window or request from an application in the background stays behind the user's work, so it cannot capture what the user types. An application receives the clipboard only once one of its windows is active, and only the active application can change it.
- No text can send an escape sequence to the terminal. Control characters in a file, a file name, a title or any widget's text are displayed as their code page 437 pictures (escape appears as `←`) and are never sent as they are. Messages printed by the command line are made safe in the same way. Text areas keep a file's control characters, so Notepad saves the file back unchanged, and text boxes accept any single line of text.
- Applications start with `python -P`, so a module planted in the desktop's working folder is not imported by them. Characters that would not take up exactly one cell, or cannot be written at all (such as a file name that is not valid UTF-8), are drawn as `?`. Crash logs are read from the end only; the newest 50 are kept, and empty logs are not kept at all.

### Builds

- A PyInstaller build of `dasha` (`dasha.spec`, `frozen/dasha_entry.py`) that can start and host applications. A copy of the program named `dasha-desktop` is the `dasha-desktop` command.

### Shortcuts and colours

- Every keyboard shortcut can be remapped in `~/.dasha/shortcuts.json` (`--shortcuts`, `--init-shortcuts`). A set of shortcuts that would leave no way out by keyboard is refused. `dasha --key-test` shows what the terminal sends for each key. `DESKTOP_KEYS` is in `dasha.shortcuts`, and `Application.shortcuts_changed()` is called when the shortcuts change while an application runs, so that it can make its menus, and their key hints, again.
- Every colour is a named role in a theme and can be overridden in `~/.dasha/colours.json` (`--colours`, `--init-colours`). A monochrome theme is used with `--monochrome` or when `NO_COLOR` is set. A terminal with no colours (`TERM` is `dumb` or a VT terminal such as `vt100`, without `COLORTERM`) gets the Monochrome theme, and no colours under any other theme.
- A theme with no colours means no colours on the screen, for every application. Dasha Framework leaves them out as it draws, even from a style written with colours or a program in a terminal window (`style.show_colours`); bold, underline and reverse remain, and anything with a background is drawn reversed, so that a highlight still shows. `theme.has_colours()` says whether the theme has any.
- Short command-line options: `-v` (`--version`), `-s` (`--shortcuts`), `-c` (`--colours`), `-d` (`--colour-depth`), `-m` (`--show-mouse`) and `-k` (`--key-test`). The colour depth and showing the mouse, given on the command line, are remembered in `settings.toml` for next time, as Settings... remembers them.
- Colours can be 24-bit RGB (`dasha.style.Rgb`, written `"#rrggbb"` in colours and theme files), as well as the 16 named colours and the 256-colour palette. Where a terminal cannot show 24-bit colour, the nearest palette colour is drawn, and on a terminal with only the 16 standard colours (such as the Linux console), every colour is drawn as the nearest of those, as the CGA showed them. Dasha Framework decides from `COLORTERM` and `TERM` (and always shows 24-bit colour on Windows), and `--colour-depth`, the `colour_depth` setting and Settings... can choose any of the three.
- Themes can be changed while Dasha Framework is running, without restarting, from the system menu's Themes or by an application calling `set_theme`. Default, Dark and Monochrome are built in, each file in `~/.dasha/themes/` adds another (`--init-theme NAME` creates one), and the choice is remembered in `~/.dasha/settings.toml`. An application running on its own starts with the theme the desktop would have: the one chosen last, the colours file, or the Monochrome theme if `NO_COLOR` is set.

### Terminals

- Supports the Windows console (through `ctypes`) and POSIX terminals (through `termios`), locally and over SSH. Dasha Framework runs on the alternate screen, hides the terminal's scroll bar where the terminal allows it, and redraws immediately when the terminal is resized.
- Mouse support (SGR reporting, motion, the wheel and double-clicks), bracketed paste, key releases where the terminal reports them, and Alt and Ctrl key combinations in their common encodings. Control characters, and characters that would not take up exactly one cell, are never sent to the terminal.
- In the classic Windows console (PowerShell or Command Prompt in their own window, and the built executable), the desktop keeps working when the window is maximised, put in full screen (Alt+Enter) and restored. When a resize leaves the console's screen buffer larger than its window, the desktop enters the alternate screen afresh and draws everything again at the window's size (`Terminal.take_cleared()` says when the screen was cleared this way). Quitting while the console is maximised or full screen brings back what the console showed before, and the lines above it, and the window stays maximised.

### Example applications

- Notepad, a text editor; Demo, a tour of the widgets, the file dialogs and an Explorer window; and Terminal. All three are in the repository's `apps/` folder with their own tests (see `apps/README.md`), and none is part of the package.
- Terminal (`apps/terminal.py`), built on `TerminalView`, runs the user's shell, or another command, in a window: bash, zsh and the like on Linux and macOS, and cmd or PowerShell on Windows (10 version 1809 or later), with colour, the alternate screen of full-screen programs, a scrollback for the mouse wheel, and text selected with the mouse to copy. A program that asks to be told of the mouse (vim, htop, mc) gets clicks, drags and the wheel (`encode_mouse`, `TerminalView.send_mouse`); Terminal > Mouse to programs turns that off so the mouse selects text, and Shift+drag selects either way. Keys the desktop keeps can be sent with Terminal > Send key. Three shortcut actions, `terminal_copy`, `terminal_paste` and `terminal_mouse`, have no keys by default. Each window is 80 by 25 inside where that fits, with a black frame and inside whatever the theme, and Alt+T and Alt+E open its menus, so those two keys do not reach the shell.
